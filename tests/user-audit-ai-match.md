# 核心功能复核：按人脸自动匹配发型与发色（5 轮）

> 需求方原话：**通过手机前置摄像头扫描人脸，让用户配合人脸位置，然后用 AI 的方式
> 或者自带的发型发色模板来实时自动匹配。核心功能是 AI 根据人脸自动生成匹配
> 合适的发型以及发色。**

## 先说结论

**改之前，「根据人脸匹配」这个核心功能是零。**

不是做得不准，是根本没有：

```
$ grep -rn "推荐|recommend|suggest|脸型|faceShape" pages utils
utils/hairstyles.js:217:  face: '几乎适配所有脸型'      ← 展示文案
utils/hairstyles.js:218:  desc: '…修饰额头又能拉长脸型。'  ← 展示文案
```

`face` 字段在详情弹层里显示给用户看，**从不参与任何判断**。
款式固定为 `currentStyle: 'bob'`，发色固定为 `currentColor: 'chestnut'`——
十款发型十二个发色，全靠用户自己横向划。

也就是说，产品实际做的是「**手动试戴**」，而需求是「**自动匹配**」。
这两件事的差别不在渲染精度，在于**有没有一个东西在替用户做决定**。

| 需求 | 改之前 | 现在 |
| --- | --- | --- |
| 扫描人脸拿到可用的测量 | 只拿脸框做位置换算 | 多算两件事：脸型比例、肤色 |
| 根据人脸匹配发型 | **没有** | 脸型 → 10 款排序，取第一 |
| 根据人脸匹配发色 | **没有** | 肤色 → 12 色排序，取第一 |
| 实时自动应用 | **没有** | 对齐后 0.6s 自动换上，并说明理由 |
| 用户不认可时的出口 | **没有** | 改判脸型 / 换成推荐 / 收起 / 自己划 |

## 第 1 轮｜核心功能为零：没有任何「匹配」

**自我否定**：前面五轮都在打磨「取景框 + 对齐」，把「让用户配合」做扎实了，
但那只解决了**输入**。输入之后没有任何决策——对齐成功的奖励是
「你看到了一顶默认的波波头」。需求里最重要的那个动词（匹配）不存在。

**做法**：新建 `utils/match.js`，纯函数，不依赖 canvas/wx，可在 Node 里直接测。

- **脸型**：从人脸框宽高比反推。框一般从发际线框到下巴，脸长 ≈ 1.28 × 颧宽，
  所以正常比例落在 0.78。`≥0.84` 偏圆、`≤0.70` 偏长、中间标准，边界留 ±0.015 死区。
- **发型**：10 款 × 3 种脸型 = 30 个适配分（0~3），每格配一句人话理由。
  打分依据是造型上的真实作用，不是文案：圆脸要拉长（顶部加高 / 垂直线条 / 收窄两侧），
  长脸要加宽缩短（齐刘海压额头 / 齐下巴的横向体积 / 两侧蓬松）。
- **肤色**：CIELAB → ITA°，皮肤科的标准分级。
- **发色**：按肤色深浅定一个目标明度（深 40 / 中 62 / 浅 88），按距离打分，
  同分再按「日常接受度」排序。

**关键决定：不猜测不出来的东西。** 微信 VKSession 只给人脸框，没有五官关键点，
所以测不出下颌角宽度——**方脸这件事就不说**，只分圆 / 标准 / 长三档。
上轮已经踩过 `anchor.angle` 的坑（文档说是数组、分量顺序未公开），
这里同理：宁可少一个维度，也不猜。

证据：`tests/face-match.js` A1–A6、C1–C11、F1–F8。

## 第 2 轮｜引擎建好了，但流程没接

**自我否定**：写了一个能排序的模块，和「产品会匹配」是两件事。
`onLoad` 里款式早就定死了（URL 参数 > 上次用的 > `'bob'`），
锁脸之后没有任何代码去问引擎「该给这个用户推什么」。

**做法**：把推荐接进对齐状态机，但**只在对齐成功时触发**。

```
对齐 locked → 等 600ms（让用户先看清画面）→ runRecommend()
  → 脸型估计器够 6 帧正脸？不够就隔 700ms 再来，最多 4 次
  → 够：排序、取第一、自动换上、弹卡片
  → 不够：什么都不说（用户一直在转头时，任何脸型结论都是编的）
```

**同时必须解决的冲突**：自动匹配会覆盖用户的选择。所以划了三条线，
只要有一条成立就**只推荐、不替换**：

1. URL 带了款（从发型库 / 分享卡片点进来，意图明确）
2. 有上次用的记录（老用户，昨天看中的那款今天还想看）
3. 本次已经手动选过

还有一条容易漏的：**自动换的款不能写进「上次用的」**。
写了的话，第二次进来 `_hasLastPick` 就成立，自动匹配从此再也不会发生——
一个只用一次的功能。

证据：G1–G11、G19–G22。

## 第 3 轮｜推荐是黑箱，而且会谎报「已换上」

**自我否定**：卡片上写「已换上『背头』」，但如果推荐款**本来就是当前款**呢？
标准脸的首选是短碎发，用户默认是波波头——换一次没问题；
可一旦推荐款等于当前款，代码走的是 `if (changed)` 才换，
卡片却照样说「已换上」。用户盯着画面看半天没变化，只会觉得功能坏了。

**做法**：把「换没换」和「推什么」拆成两个字段，三种说法分开：

| 状态 | 文案 | 按钮 |
| --- | --- | --- |
| 推荐款 ≠ 当前款且已应用 | 已换上「背头」 | 无 |
| 推荐款 = 当前款 | 「短碎发」正适合你的脸型 | 无 |
| 用户表过态，没替换 | 更推荐「齐刘海短发」 | 换成这款 |

**顺带修的同一类问题**：脸型贴边界时（比如宽高比 0.845，离圆脸线 0.005）
原来照样报「标准脸」。改成报「接近标准」——用户是拿这句话判断
「它测得准不准」的，装准比不准更伤。

证据：J1–J6、I7b。

## 第 4 轮｜发色完全不看脸，而肤色一量就翻档

**自我否定**：第 1 轮把肤色算出来了，但**没有验证它准不准**。
拿同一张中等肤色的样本，只改整体亮度试了一下：

| 场景 | ITA° | 判定 |
| --- | --- | --- |
| 中性光 | 30 | 中等 |
| 画面暗 25% | **-1** | 偏深 |
| 画面亮 30% | **45** | 偏白 |
| 暖光 +30%R | 23 | 中等 |
| 冷光 -15%R | 45 | 偏白 |

**同一个人，自动曝光一动，发色推荐就整个翻档。** 这不是理论风险，
是拿数字跑出来的。ITA° 的分母是 b*、分子是 `L*-50`，
而手机自动曝光每帧都在调，人脸又是测光主体——这条路的绝对亮度不可信。

**做法**：加一路**增益无关**的旁证。曝光是三个通道同乘一个系数，
所以 HSV 饱和度 `(max-min)/max` 不受影响；而肤色越深，饱和度越高。

两路都指向同一档才敢用；打架就标 `confident=false`，页面据此：

- 仍然显示发色建议（不装死）
- **不自动替换**用户的发色
- 卡片上明写「画面光线偏色，这条发色仅供参考」

实测：中性光下六档肤色两路全部一致（不是一味保守）；
偏暗 0.75×、偏亮 1.3×、暖光 +30%R 三种情况必然打架。

证据：K1–K9、D1–D5、E1–E7。

## 第 5 轮｜流程边界：快门、切摄像头、卡片占位

**自我否定**：三个只在真机上才会撞到的时序问题。

**① 拍照瞬间被自动换款。** 推荐有 600ms 延迟 + 最多 4 次重试，
完全可能正好落在用户按下快门之后。`_captureLook` 冻结的是**按下那一刻**的款，
所以照片本身没错，但「刚拍的和刚才看到的」对不上，用户会以为照片错了。
→ `runRecommend` 遇 `shooting` 让路（重试），`applySkin` 遇 `shooting` 延后 500ms。

**② 切摄像头后沿用旧脸型基准。** 脸型估计器取的是「窗口内最大宽高比」，
不重置的话上一台摄像头的最大值会一直压着，新的观测永远改不动结论。
→ `switchCamera` 里和 `_yaw.reset()` 一起 `_shape.reset()`。

**③ 卡片把面板顶高了 191pt，盖住半张脸。** 这条是截图量出来的，不是猜的：

| 状态 | 面板高度 | 面板顶边 | 取景框下沿 |
| --- | --- | --- | --- |
| 原来（无卡片） | 265pt | 402pt | 404pt |
| 卡片展开、面板照常 | 415pt | **213pt** | 404pt ← 盖住 191pt，从鼻子往下全没了 |
| 卡片展开 + 三块让位 | 286pt | 381pt | 404pt ← 只压到下巴尖 |
| 收起态（一行小条） | 296pt | 371pt | 404pt |

→ 卡片展开时**接管面板**：款式条、色带、标题行暂时让位，卡片本身
已经写全了「哪款、为什么、什么色、判得准不准」。任何一次点击
（卡片任意位置、选款、选色、进微调）立刻收起；不点也会在 7 秒后
收成一行小条，点小条可重新展开。

证据：L1–L8、M1–M10、I7d–I7e；截图 `tests/out/rec4.png`。


## 遗留问题（如实记下，没做）

1. **脸型阈值是经验值，需要真机校准。** 0.84 / 0.70 建立在
   「人脸框从发际线框到下巴」这个假设上，不同基础库框的范围不一样，
   整体会平移。缓解手段是宽死区 + 允许用户改判，但第一次上真机
   应该拿 20 张不同脸型的 anchor 日志回归一遍。
2. **没有方脸 / 心形脸。** 只有人脸框，没有下颌角宽度，测不出来就不说。
   要做得靠 `anchor.points`，但官方没公开关键点顺序，猜索引的代价
   （整头发型持续倾斜）比不做更大。
3. **肤色只判深浅，不判冷暖。** 冷暖要靠色相，而手机白平衡不可知，
   同一张脸在暖光/冷光下 hue 能差 15°。所以「你适合冷调还是暖调」
   这句话这个产品永远不该说。
4. **推荐不记忆。** 自动匹配每次进页面重算，不落库。
   好处是不会拿旧结论套新光线，坏处是用户「我就喜欢它推的那款」
   这件事没法沉淀——真要做得加一个「记住这次推荐」的开关。

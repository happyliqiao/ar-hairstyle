# 核心功能复核记录（取景框范式 · 5 轮）

产品定义（本轮基准，来自需求方）：

> 通过手机**前置摄像头**扫描人脸，画面上有一个**类似人脸验证的固定人脸形状框**，
> 让用户**主动配合**把脸放进框里，再用 AI 或自带的发型发色模板**实时自动匹配**。

复核维度三条：**核心功能是否有误 / 效果是否有偏差 / 流程是否异常**。
方法同前：每轮先提否定性假设，用代码和测试验证，只记本轮新问题。
对应回归：`tests/guide-frame.js`（69 项），已并入 `node tests/all.js`（50 套）。

---

## 结论先行：核心功能确实有误

按上面的定义逐条对照，改之前的产品**只做到了第 4 条的一半**：

| 需求 | 改之前 | 现在 |
| --- | --- | --- |
| 前置摄像头 | 有，且支持前后切换 | 不变 |
| 固定的人脸形状框 | **完全没有**。画面上只有一句「把脸放进画面中」的状态文字 | 固定瓜子形框，三态（idle / aligning / locked） |
| 让用户主动配合 | **不成立**。发型跟着脸走，脸在哪儿发型跟到哪儿，用户不需要配合任何事 | 判定脸是否在框内，给出「往右一点 / 靠近一点 / 头摆正一点」 |
| 实时自动匹配 | 有几何贴合，但"检测到脸"就等于"锁定成功" | 对齐后才叫锁定，未对齐时如实说没对齐 |

一句话：**原来做的是「跟随」，不是「匹配」；缺的不是渲染精度，是交互范式。**

## 第 01 轮｜画面上根本没有那个框

- 路径：扫码进首页 → 开始试戴 → 举起手机对准自己。
- 否定：产品定义的第一件事是「有一个固定的人脸形状框」。实际页面里
  只有左上角一个状态胶囊在说「把脸放进画面中」，画面本身没有任何参考物。
  用户不知道"放进去"是放到哪里、要放多大、偏了怎么算。
  这不是文案问题，是**功能缺失**：没有框就没有"配合"这个动作的对象。
- 一个必须说清的区分：上一轮我删掉的是 `drawFaceGuide()` —— 那是**虚拟头型**
  （画一个假人头 + 假发冒充效果，模拟器里用的）。取景框不是虚拟头型：
  它是一条参考线，本身不产生任何发型效果，删错了东西和漏掉了东西是两回事。
- 修复：`utils/face-fit.js` 新增 `guideFrame(cw, ch)`，固定框宽 = 屏宽 × 0.60、
  框心 y = 屏高 × 0.40、高宽比 1.22。wxml 用 JS 算出的 px 值内联绘制，
  **几何只有一份来源**——如果 CSS 写一套、JS 判一套，就会出现
  「框明明套住了脸，却提示没对齐」。
- 证据：A1–A7、F1–F2。

## 第 02 轮｜框画出来了，但它是装饰

- 路径：脸偏在画面左下角，看页面给什么反馈。
- 否定：只画框不判定，用户只能靠肉眼比对，不知道自己算不算"进去了"。
  更根本的是：`anchorToBox()` 把 `faceAnchorToBox()` 算好的
  `face: {cx, cy, w}`（脸在屏幕上的真实位置和大小）**直接丢掉了**，
  只回 `x/y/w/h`（发型框）。于是页面永远不知道"脸偏左还是偏右"，
  只能干巴巴说一句"把脸放进画面中"。
  数据已经算出来了，却在最后一步被扔掉——这是最典型的"功能有，但没接上"。
- 修复：`anchorToBox` 保留 `face`；新增 `judgeAlign(face, viewport, angle)`
  判定偏移量、大小比例、倾斜角；提示最多给两条（三条以上用户记不住先做哪个），
  且**大小优先于位置**——距离不对时怎么挪位置都白挪。
- 证据：B1–B11、E1。

## 第 03 轮｜"太近了"这件事，产品永远测不出来

- 路径：把手机贴到脸上。
- 否定：`face-fit` 会把脸宽夹到取景宽的 9%~78%，目的是防止发型糊满屏幕。
  但夹取发生在判定之前，于是「贴到镜头上」和「正常手持」算出来是同一个数，
  `ratio` 永远落在容差内 → 用户永远等不到「后退一点」。
  旧的上界 0.78 更离谱：脸宽 78% 屏宽时，发型宽是 1.56 屏宽，早就糊成一团，
  产品却还在说"大小合适"。
  这是**用夹取替用户凑合**，和"让用户主动配合"正好相反。
- 修复：
  1. `faceAnchorToBox` 额外返回 `rawW`（夹取前的真实屏幕脸宽）；
     `judgeAlign` 用 `rawW` 判距离，绘制仍用夹取后的值防糊屏。
  2. 夹取区间收紧到 0.26~0.58，与取景框（框宽 0.60 屏宽）对齐；
     旧值 0.09 意味着脸只有 34px 也能画出正常大小的发型。
  3. 判定上界取 1.12，**比夹取上界更紧**：夹取是为了防糊屏，
     判定是为了提醒用户后退，两者目的不同，不能共用一个阈值。
- 证据：C1–C7。

## 第 04 轮｜流程缺了「对齐中」这一态

- 路径：脸只露出半张、贴在屏幕角落，看状态栏写什么。
- 否定：`onFaceAnchor` 只要收到 anchor 就写「已锁定人脸 · 实时试戴中」。
  用户看到的是一顶明显错位的发型，配一句"已锁定"——这比不提示更糟，
  因为他会认为自己操作错了，而不是产品没对齐。
  流程上应该是：寻找 → 对齐中（给方向）→ 已对齐（才叫锁定），
  原来把中间那一态整个跳过了。
- 修复：三态状态机 `idle / aligning / locked`，文案跟着走：
  - `idle`：还没检测到脸，框是白色虚线，文案「把脸放进框里」
  - `aligning`：检测到但没对齐，框变金色实线，文案就是方向提示
  - `locked`：对齐了，框淡到 0.34，文案「已对齐 · 实时试戴中」
  另外三处必须跟着复位，否则状态会"粘住"：
  - 丢脸（`removeAnchors`）→ 回 idle，文案回「把脸放进框里」
  - 切摄像头 → 清 `_align`。后置摄像头不镜像，沿用前置的判定结论会显示成"已对齐"
  - 每帧都算，但**只有状态或提示真的变了才 setData**。每帧 setData 会让
    引导文字一闪一闪，低端机上还会把帧率拖下来。
- 证据：E2–E11。

## 第 05 轮｜镜像会把方向提示说反；浅色背景下框会消失

- 路径 A：开镜像（默认就是开的）→ 脸偏在屏幕右侧 → 看提示。
- 否定 A：前置摄像头画面是左右翻转的。如果方向提示用**原始 anchor 坐标**算，
  「往左/往右」就会和用户眼睛看到的相反 —— 用户照着提示挪，越挪越偏。
  这是 AR 类产品最常见的低级事故，而且极难自查（开发者自己看到的是对的）。
- 修复 A：判定一律用**已经过镜像的** `face.cx`（`faceAnchorToBox` 内部
  `if (mirror) cx = cw - cx` 之后的值），所以得出的左右就是屏幕上的左右，
  不需要再翻一次。测试 D1–D3 用同一锚点分别跑不镜像/镜像，断言两句提示必须相反。
- 路径 B：站在白墙前或窗户边。
- 否定 B：框是白色虚线，在浅色背景上会彻底消失，用户找不到框在哪。
  这不是美观问题，是可用性问题 —— 而自拍场景里白墙是最常见的背景。
- 修复 B：给框补一圈 1px 暗描边（`box-shadow`），形成"白线 + 暗边"，
  深底亮底都可见。同时**删掉了四角括号**：截图对比发现，
  椭圆 + 四个外接矩形角的组合在视觉上互不相干，看起来像
  「一个蛋加四个孤立的拐角」，反而干扰判断。轮廓改成上宽下窄的瓜子形
  （`border-radius: 52% 52% 46% 46% / 46% 46% 54% 54%`），接近人脸的真实轮廓。
- 证据：D1–D3、F3–F5，以及 `tests/out/guide3.png` 三态截图（含浅色背景）。

## 遗留问题 1 与 3：已解决

### 问题 1｜侧脸判定不准

**根因**：微信 `VKFaceAnchor` 只给 `angle`（画面内旋转 = roll），
**不给 yaw**。所以「用户转了 45° 脸」这件事，从 API 层面是拿不到的。

**做法**：从几何反推。人脸检测框的宽度 ≈ 正脸宽度 × cos(yaw)，
越转越窄。于是「当前宽高比 ÷ 该用户历史最大宽高比」就是 cos(yaw) 的估计，
反余弦即可还原角度。`face-fit.createYawEstimator()` 负责这件事。

三道阈值，缺一道都会出问题：

| 阈值 | 值 | 作用 |
| --- | --- | --- |
| 相对判定 | rel < 0.82（yaw ≈ 35°） | 主要判据 |
| 绝对兜底 | aspect < 0.50（yaw ≈ 60°） | 不依赖基准，第一帧就生效。否则「一进页面就是大侧脸」会把基准污染成侧脸值，永远判成"正对" |
| 基准下限 | ref < 0.55 | 这台设备/这版基础库给的人脸框本来就窄（不同算法框的范围不一样），相对判定不可信，关掉，宁可不提示也不误报 |

另外加了 `degenerate` 标记：连续 12 帧宽高比波动不到 4%，
说明框被「正方形化」了，yaw 无从反推。此时不做任何提示 ——
假阴性可以接受，误报「正对镜头」会让人莫名其妙。

**连带修掉的一处耦合**：距离判定必须从「脸宽」改成「脸高」。
yaw 只压缩宽度，几乎不影响高度。如果继续用宽判距离，
用户把头转过去 40°，检测框变窄，产品就会喊「靠近一点」——
而他人根本没动，只是转了个头。用高度判距离，两条判定互不污染。

### 问题 3｜对齐后框只淡化不消失

**做法**：对齐满 3 秒淡出（`GUIDE_FADE_MS`），一偏离立刻回来。

- 不立即隐藏的原因：用户稍微一动就偏了，没有参照他不知道自己偏了。
- 不永久保留的原因：框的职责只是「把脸引进构图区」，引到位后它就只剩干扰。
- 用 `opacity` 过渡而不是 `wx:if` 删节点：删节点是「啪」地消失，读起来像坏了；
  淡出 0.4 秒读起来是「它自己退场了」。保留节点也让「一偏离就回来」没有一帧空白。
- 三处必须复位：丢脸、切摄像头、离开页面（清 `_guideFadeTimer`）。

## 过程中发现的两个额外缺陷

### A. `anchor.angle` 是数组，不是数字

官方文档写明 `VKFaceAnchor.angle` 的类型是 `Array<number>`（只说「人脸角度信息」，
没公开分量顺序）。旧代码 `clampAngle(anchor.angle || 0)` 直接把它当数字用：
数组进 `clampAngle`，`a > limit` 是 NaN 比较恒为 false，函数原样返回数组，
最后 `trackedAngle + rotRad` 变成字符串拼接，`ctx.rotate('0,0,0.1')` 得到 NaN ——
整个造型的旋转会失效。

修法：新增 `pickRoll(anchor)`。数字直接用；**数组一律返回 0，不猜分量**。
猜错分量会让整头发型持续倾斜，用户看到的是「头发歪了」而不是「角度没识别」，
比不跟随更糟。证据 G13–G17。

### B. 归一化坐标的映射可能偏（本轮未改，需要真机验证）

官方文档和官方示例都表明 `origin` / `size` 是**相对视窗的 0~1 归一化**：

```js
// miniprogram-demo / face-detect
flattenPoints.push(x * 2 - 1, 1 - y * 2)   // 归一化直接转 NDC
```

而 `faceAnchorToBox` 的归一化分支是 `fx = o.x * frame.w`，之后又走了一遍
cover 映射（`* scale + offX`）。如果归一化真的是相对视窗，这里会多缩一次：
在 375×667 视窗、480×640 帧下，`o.x = 0.2` 算出来是 37px，正确值应为 75px。

**没改的原因**：这条分支在本项目里从未在真机上被验证过（真机很可能返回的是
像素坐标，走的是另一条路）。改它等于改一条没有对照数据的路径，
风险高于收益。已在此记录，等真机日志确认后单独处理。

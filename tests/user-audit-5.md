# 用户视角自查优化记录（去掉虚拟卡通化 · 5 轮）

范围：产品里所有「看起来像能力、其实只是示意」的东西。
方法：同前 20 轮 —— 每轮先提出否定性假设，用代码和测试验证，只记本轮新问题。
对应回归：`tests/no-virtual-preview.js`（47 项），已并入 `node tests/all.js`（49 套）。

这一轮的判断标准只有一条：
**画面上出现的每一撮头发，都必须对应用户脸上或他自己动手定位的位置；
否则宁可不画，也不能画一个"演示效果"。**

## 第 01 轮｜模拟器里的假人头

- 路径：开发者用微信开发者工具打开试戴页。
- 否定：页面用 `drawFaceGuide()` 画了一个椭圆"头型"，再在它上面挂一顶发型。
  模拟器根本没有摄像头画面，这个头型是纯虚构的；开发者会据此认为
  "识脸已经跑通了"，运营会拿截图当效果图，用户扫码前看到的预览也是假的。
- 修复：删掉 `drawFaceGuide()` 与整套虚拟头型绘制；`render()` 在
  `isDevtools` 时清空画布后直接返回，一帧都不画。wxml 的模拟器分支改为
  纯引导文案："模拟器没有摄像头，不提供虚拟头像或合成照片"，画布加
  `is-off` 关闭命中，底部操作区整体隐藏（没有画面就没有可操作的对象）。
- 证据：1.1 / 1.2。

## 第 02 轮｜没识到脸也挂一顶悬空发型

- 路径：进页面，人还没把脸放进画面；或识脸丢了两秒以上。
- 否定：`computeBox()` 在没有任何 anchor 时会退回"屏幕中央默认位置"，
  于是相机画面上漂着一顶不属于任何人的发型。用户会以为识脸在工作，
  转头发现发型不跟脸走，只会判定"这功能是假的"。
- 修复：`computeBox()` 在 `!faceFound && !manualOn` 时返回 `null`；
  `render()` 改成**先 `clearRect` 再判断空框**（顺序反了会留下一帧残影）；
  空框时同时把 `lastBox` 清掉，避免拍照复用过期坐标。
  丢锚点后给 2.5 秒宽限期（`_lostTimer`），期内仍跟着脸、避免抖动，
  期满主动重绘一次把发型擦掉；`onUnload` 补上 `_lostTimer` 的清理。
- 证据：2.1–2.5、2b.1–2b.5。

## 第 03 轮｜识脸不可用只留一句"可拖动微调"

- 路径：旧版微信（无 `createVKSession`）、创建 session 抛异常、
  `session.start` 返回错误码。
- 否定：三条降级路径都只把状态文字改成"…可拖动微调"，但画布是空的。
  用户不知道要拖什么、往哪拖，拖了会不会有反应；而且"可拖动微调"这句话
  本身就在暗示功能已经可用。这是最典型的"假装能用"。
- 修复：新增 `arUnavailable` 状态，三条路径都如实置位并改文案
  （"这台设备不支持自动识脸" / "自动识脸没能启动"）；
  画面中上部出现一张降级卡片，写明原因并给一个**「手动定位」按钮**。
  点按钮才进入手动模式（`enterManual()`），状态栏随即改写成
  "手动定位 · 拖动对齐发际线，双击复位" —— 全程不冒充 AR。
  识脸正常时 `enterManual()` 直接返回，不会把"已锁定人脸"改写成手动。
  顺带修掉同一类的一处：款式详情里的「识脸状态」原本只有
  「已锁定 / 手动定位」两态，没识到脸也没手动时照样显示"手动定位" ——
  改成「已锁定 / 手动定位 / 未识别到」三态。
- 证据：3.1–3.12。

## 第 04 轮｜微调滑块是摆设

- 路径：识脸不可用时拉"大小 / 位置 / 旋转"三个滑块。
- 否定：三个 `*Changing` 只写 `sizeVal/yVal/rotVal` 再 `render()`，
  而 `computeBox()` 此时返回 `null` —— 滑块拖到底，画面一动不动。
  用户的第一反应是"卡死了"，第二反应是"这排控件是装饰"。
  同一件事（手动摆位置）在拖画面时能出图、拉滑块时不能，本身就自相矛盾。
- 修复：六个滑块回调（3 个 `*Changing` + 3 个 `*Change`）统一调用
  `enterManual()`，与拖动画面共用同一条路径、同一句文案。
  `enterManual()` 内部有 `manualOn` 早退，连续 `changing` 不会每帧
  `setData`；识脸正常时也早退，不抢状态文案。
- 证据：4.1–4.7。

## 第 05 轮｜快门拍出"没有发型的原图"

- 路径：没识到脸（或识脸失败）时按快门。
- 否定：`compose()` 里是 `if (box) drawHair(...)` —— 框为空时它不报错、
  不提示，安安静静把一张**只有自拍、没有发型**的照片写进相册和本地记录。
  用户以为拍到了试戴效果，回头翻记录才发现是原图，而照片已经在系统相册里了。
  更隐蔽的是 `capture()` 取的是 `this.lastBox || computeBox()`，
  而 `lastBox` 只在有框时赋值 —— 脸走了十秒，它还是脸走之前的那个坐标，
  于是照片上会出现一顶漂在背景里的发型。
- 修复：`capture()` 在 `setData({shooting:true})` 之前先算 `shotBox`，
  为空就直接拦下并给出可执行的下一步（"先点「手动定位」，再按快门" /
  "把脸放进画面再按快门"），不消耗一次快门、不进入 `shooting` 状态；
  冻结框改用这个已校验的 `shotBox`。`compose()` 里补一道兜底：
  真走到空框就 `hideLoading` + 解冻 + 复位 + 提示重拍，绝不静默存原图。
- 证据：5.1–5.6。

## 这一轮之后，产品不再做的事

| 以前会做 | 现在 |
| --- | --- |
| 模拟器里画假人头 + 假发型 | 只给"用真机预览"的引导，一帧不画 |
| 没识到脸时在屏幕中央挂发型 | 画布留空，状态提示"把脸放进画面" |
| 识脸不可用时说"可拖动微调" | 说明原因 + 给「手动定位」按钮 |
| 滑块拖到底画面不动 | 拉滑块 = 进入手动定位，画面立即响应 |
| 没有定位也存一张原图当"试戴照" | 拦下快门，说清下一步 |

保留的降级能力只有一条：**手动定位**。它不是虚拟示意 ——
位置由用户亲手摆，状态栏也明说是手动，出了图就是用户要的那张图。

## 六个维度 · 50 轮记录

### G1 屏幕形态（R01–R10）｜此前从未测过

| 轮次 | 场景 | 实测与结论 |
| --- | --- | --- |
| R01 | 375×667 常规竖屏 | 框 225×274.5，完整在屏内 → 通过，确认新公式对手机零改动 |
| R02 | 320×568 小屏 | 框上沿 110 / 下沿 344，不压顶部栏也不压面板 → 通过 |
| R03 | 390×844 全面屏 | 框心 337.6 = 0.40×屏高 → 通过 |
| R04 | 768×1024 平板竖屏 | **框高 562px = 55% 屏高**，改后 46% → 修 |
| R05 | 1024×768 平板横屏 | **框高 750px = 98% 屏高、框宽占 60% 屏宽**，改后 46% / 28% → 修 |
| R06 | 844×390 折叠屏展开 | **框上沿 -153px，框根本不在屏幕里**，改后 66 / 246 → 修 |
| R07 | 360×1280 分屏极窄高 | 框宽占 60%，合理 → 通过 |
| R08 | 横屏下真实人脸判对齐 | **ratio=0.28，永远提示「靠近一点」，永不 locked → 自动匹配一次都不触发**，改后 ratio=0.95 / locked → 修 |
| R09 | 宽屏下发型框尺寸 | **438.9px（超过半屏），比取景框大近 3 倍**，改后 276.9 → 修 |
| R10 | 非法尺寸输入 | 0 / 负 / NaN / 字符串 / Infinity 有 5 种会画出脏几何 → 统一返回 null → 修 |

**根因**：`guideFrame` 只按屏宽算框；`judgeAlign` 又用「脸高 / 框高」判距离。
框一大，比值永远偏小，用户被无限要求「靠近一点」，核心的自动匹配在这类设备上静默失效。
修法：框同时受屏宽与屏高约束（框高 ≤ 46% 屏高，手机原本就在 41%，不受影响）；
`faceAnchorToBox` 的脸宽夹取区间改为跟着框宽走，不再写死屏宽。

## 三次自我否定（这一轮真正有价值的部分）

1. **R45 第一次写错了场景**：把脏值设在 `sizeVal` 上，但 `computeBox` 里 `(sizeVal || 100)` 会把 NaN 兜成 100，
   缺陷根本没被触发。改断言去凑结果是最容易的做法，但那是自欺；改成真正会漏进来的 `dragDX`（`touchPoint` 只验
   `typeof === 'number'`，NaN 也过）后，才测出「NaN 几何交给 drawHair」这条真问题。
2. **R19 的第一次修复过严**：写成「只要 `faceFound=false` 就拦快门」，全量回归立刻挂了 5 套
   （拍照复位 / 缩略图链路 / 端到端旅程 / 用户视角 20 轮 / 去卡通化）。查清是旧套件模拟的是
   「从没丢过脸的干净会话」，不该被这条规则管。把条件收紧为「确实发生过失脸（`trackedLostAt`）且尚未重新识到」，
   既保住修复，又不误伤手动定位、相机刚启动等正常路径。5 套全恢复，没有改任何一条旧断言。
3. **`no-virtual-preview.js` 的 2b.3 是假通过**：那个页面实例没跑 `onLoad`，`dragDX` 是 undefined，
   「宽限期内还跟着脸」的断言一直建立在一个 NaN 框上。新的有限性校验让它暴露出来。
   补上 `dragDX/dragDY = 0` 的模拟状态（断言不变），而不是放宽产品校验。

## 遗留（如实记下，没做）

- 折叠屏 / 平板 / 横屏只做了**几何与状态**验证；真机上相机预览是否同样按 cover 铺满、横屏下前置画面是否需要额外旋转，仍需实机确认。
- `onResize` 只重算画布与取景框，不重新探测摄像头帧尺寸（帧尺寸由相机决定，与窗口比例无关；重新探测会和肤色采样抢 `onCameraFrame`）。
- R19 拦的是「确实丢过脸」的快门。瞬时丢一帧 anchor（转头、手挡）仍会拦一次，属于「宁可重按一次，也不存废片」的取舍。
- `faceAnchorToBox` 的归一化坐标分支仍缺真机 anchor 日志核对（前几轮就记过，本轮未解决）。

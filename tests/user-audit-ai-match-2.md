# 自动匹配复核（第 6 轮 · 真人使用视角 · 5 轮）

> 需求方原话：**核心功能是 AI 根据人脸来自动生成匹配合适的发型以及发色。**
> 这一轮不看「有没有做」，只看**做出来的东西在真人手里会不会静默失效**。

## 先说结论

上一轮（`user-audit-ai-match.md`）把「匹配」从零建了起来，五轮分别解决了
引擎、接线、谎报「已换上」、曝光翻档、快门竞态。功能是通的。

但把手机真的举到脸前，会发现一个共同点：**五个问题全都不是「算错了」，
而是「该给结论的时候一声不吭」**——用户看到的不是错误答案，
是「说好的自动匹配一次都没出现」。

| 场景 | 改之前 | 现在 |
| --- | --- | --- |
| 用户站得笔直、一帧不晃 | 判成「框被正方形化」→ **永远不推荐** | 正常给结论 |
| 进页面先转了下头（3.4 秒内没摆正） | 4 次重试用尽 → **整个会话永久关闭** | 摆正就补上，只放弃定时器不放弃功能 |
| 暗光下第一轮采不到肤色 | 发色匹配 **永久消失** | 最多重试 3 轮（约 10 秒） |
| 自动换成短碎发 / 自然黑 | 横滑条上 **一张高亮的都没有** | 条跟着滚到那一项 |
| 不接受第一名 | 只有一个答案，只能自己乱划 | 卡片给「换一款」，同档 3 个候选 |
| 脸型落在边界上（0.845） | 报「标准脸」，100% 肯定 | 报「接近标准」+「脸型在边界上」 |

## 第 1 轮｜越配合的用户，越拿不到推荐

**自我否定**：上一轮为「SDK 把框输出成正方形」加了一道退化检测，
判据是「连续 12 帧宽高比波动 < 4%」。写的时候只想着「框稳 = 假数据」，
忘了另一件更常见的事：**用户举着手机不动的时候，框也很稳。**

拿数字验了一下：

```
稳定 0.78 脸 20 帧（±1 抖动） → {"shape":null,"degenerate":true,"ready":false}
轻微抖动（±4）               → {"shape":"oval","confidence":0.6,"ready":true}
```

**站得最稳的用户被判成假数据，手抖的用户反而拿到结论。**
而且这个假阴性没有任何提示：页面不弹卡片、不写「测不准」，
用户只会以为这个功能不存在。

**做法**：退化判定必须同时满足两个条件 —— **稳**，并且**值接近 1**。
真实人脸宽高比在 0.6~0.95，被正方形化的框恒等于 1.0，两者本来分得开。

```js
const steady = seen >= 12 && (maxAspect / minAspect) < 1.04
const square = minAspect >= 1 - 0.03 && maxAspect <= 1 + 0.03
const degenerate = steady && square     // 改之前只有 steady
```

**证据**：N1–N6（稳定标准脸 / 完全静止 / 真正方形化 / 正方形化+抖动 / 稳定圆脸 / 稳定长脸）。

## 第 2 轮｜「测不出来」被写成了「功能关闭」

**自我否定**：`scheduleRecRetry` 在次数用尽时做了两件事 —— 停掉重试，
**并且把 `_recDone` 置为 true**。后者是个开关，一旦置位，
`maybeRecommend` 直接 return，这一整次会话再也不会匹配。

时间账很简单：对齐后等 0.6 秒 + 4 次重试 × 0.7 秒 = **3.4 秒**。
进页面后 3.4 秒内没攒够 6 帧正脸，功能就没了。

而试发型时最自然的动作是什么？**转侧脸看看效果。** 转过去的那一刻，
yaw 门控把帧全部挡掉，正脸帧数停在原地，3.4 秒一到，功能关闭；
用户转回来、站定、看着屏幕等 —— 什么都不会发生。

**做法**：把「放弃定时器」和「放弃功能」拆开。

- 次数用尽只停掉 700ms 的重试链，**不置 `_recDone`**；
- `maybeRecommend` 每帧都在跑，预算用完之后改成「每帧看一眼估计器」，
  一旦 `ready` 就立刻给结论（不再等 600ms，用户已经等了好几秒）；
- `_recDone` 只在一件事之后置位：**真的给出过结论**，或者用户主动收起卡片。

**证据**：P1–P6。
其中 P5 走的正是那条真实路径：正脸 4 帧（不够 6）→ 侧脸 20 帧 → 重试跑完 →
转回正脸 → 结论补上。

## 第 3 轮｜发色匹配一次采不到，就永远没有

**自我否定**：肤色采样只做一次，这本身没错（常开帧监听会发热）。
但代码里有两处让它变成「一次失败 = 永久关闭」：

```js
if (this._skinStarted) return
this._skinStarted = true              // ← 先置位
if (!this._faceRect || !this.frameSize) return   // ← 再判断
```

1. 置位在守卫**之前**：万一调用的那一刻人脸框还没算出来，开关就焊死了。
2. 采不到（暗光、逆光、脸偏出框、大框眼镜）时直接 `applySkin(null)` 收工，
   没有任何重试。

结果：**「AI 匹配发型和发色」里的发色那一半，对暗光下的用户整场不存在。**
而用户挪到窗边只需要两秒。

**做法**：守卫移到置位之前；采空时复位开关并排一轮重试，
最多 3 轮、间隔 2.5 秒；期间卡片继续显示「正在测肤色…」（不装死），
3 轮都失败才收掉，并且**仍然不编一个肤色出来**。
另外，`onCameraFrame` 不存在或直接抛错时，把重试预算一次用掉 ——
那不是光线问题，重试也不会好。

**证据**：Q1–Q9。Q8 专门守「守卫顺序」，Q6 守「不许无限常开帧监听」。

## 第 4 轮｜换上了，但条上找不到是哪一款

**自我否定**：`stripAnchor`（横滑条定位）只在 `onLoad` 设一次。
自动匹配换上的款如果排在锚点**左边**，用户收起卡片后看到的是一排
**没有一张高亮**的发型卡 —— 画面上确实换了头发，条上却找不到。

这不是假想，两个最常走的分支都落在左边：

| 场景 | 锚点（默认） | 自动换上的 | 位置关系 |
| --- | --- | --- | --- |
| 标准脸（最多） | 波波头 第 3 张 | 短碎发 **第 2 张** | 在锚点左侧 |
| 深肤色 | 栗棕 第 3 个 | 自然黑 **第 1 个** | 在锚点左侧 |

**做法**：`applyStyleId` / `applyColorId` 在**自动换款**或**此刻条被卡片挡着**时
同步锚点。用户亲手点条上的卡片时**不重设** —— 否则会把刚点的那张甩到最左边
（这条注释上一轮就写在 wxml 里，一直没落到代码上）。

**证据**：R1–R7。
另外复测了卡片高度，确认新加的按钮没有把面板顶高：
`PANEL p0=289 p1=289 p2=316 p3=296`（改之前 286 / 286 / 313 / 296），
面板顶边 378，取景框下沿 404 —— 仍然只压到下巴。

## 第 5 轮｜一个脸型只有一个答案，还把这个答案说得很确定

**自我否定**：两个问题，都在「卡片」这一层，都在丢信息。

**① 只给第一名。** `applyShape` 取 `bestStyle()`，排序里第 2、3 名直接扔掉。
脸型只有三档，于是**同一档的所有用户拿到同一款**，第二次进来还是它。
用户不接受，就只剩「自己横滑 10 款」这一条路 —— 而哪几款也合适，
引擎本来就算出来了。这不是算法问题，是**只递了半张纸**。

**② 置信度被抹平。** 分类器在边界附近返回 `label: '接近标准'`、
`confidence: 0.6`（上一轮专门加的诚实标签），但 `runRecommend` 只把
`est.shape` 传下去，`applyShape` 又用 `SHAPE_LABEL` 常量重新拼标签 ——
**那句「接近标准」在页面上从来没有出现过**，用户看到的是 100% 肯定的
「标准脸」。而用户正是拿这句话判断「它测得准不准」。

**做法**：

- `rec.alt` 带上同档前三名（适配分 ≥2），卡片上给一个「换一款」胶囊，
  点一下轮换并真的应用；轮换完一圈回到第一名。
- `runRecommend` 透传 `label` / `confidence`；边界时标签写「接近标准」，
  底部那行「判得不准？」换成「**脸型在边界上**」—— 不加行高，只换文案。

| 脸型 | 同档候选 |
| --- | --- |
| 偏圆 | 长直发(3) / 背头(3) / 寸头(2) |
| 标准 | 短碎发(3) / 波波头(3) / 大波浪(3) |
| 偏长 | 波波头(3) / 齐刘海短发(3) / 羊毛卷(3) |

**一个必须记下来的坑**：「换一款」最初放在标题行，和「换成这款」并排，
375pt 上正好换行 —— 卡片高 23pt，面板从 313 顶到 336，重新压到脸上。
挪到理由行右侧当小胶囊后回到 316（只多 3pt）。**布局是量出来的，不是看出来的。**

**证据**：S1–S10、T1–T6；截图 `tests/out/rec6.png`、`rec6-p2.png`。

### 退化判定（第 1 轮）

```

  稳定 0.78 脸 20 帧 → {"shape":null,"degenerate":true,"ready":false}   ← 最配合的用户被判假数据
```

## 遗留问题（如实记下，没做）

1. **进页面时如果一直是侧脸，会判成长脸。** yaw 门控是**相对**的
   （`当前宽高比 / 历史最大值`），基准由自己建立：如果前 6 帧全是 30° 侧脸，
   基准就是侧脸的宽度，`rel = 1`，这些帧会被当成正脸收下。
   没有绝对头姿（`anchor.angle` 分量顺序未公开），这个洞补不上，
   只能靠卡片上的「判得不准？圆/标准/长」让用户自己改判。
2. **脸型阈值仍需真机校准**（0.84 / 0.70）。这是上一轮就记下的，
   本轮没有真机数据，结论不变。
3. **推荐不落库**：自动匹配每次进页面重算，不记「上次推荐了什么」。
   好处是不会拿旧结论套新光线，坏处是「我就喜欢它推的那款」没法沉淀。
4. **`perf-budget` 的 50ms 是绝对墙钟阈值**，这台机器上 10 张缩略图冷生成
   63~88ms（`utils/hairstyles.js` 本次一个字节没改）。已改成按「加载模块耗时」
   折算机器速度系数后判定，并把系数打印出来 —— 代码真的多画一层发丝照样会超。
   但**这台机器的绝对耗时确实高于预算制定时的那台**，值得在真机上再量一次。
5. **多张脸入镜**（两个人一起试）没有处理：估计器取窗口最大值，
   两个人轮流被框住时结论会取「更圆的那张脸」，卡片文案对不上任何一个人。
   要做得先加「框跳变检测」，本轮没做。
